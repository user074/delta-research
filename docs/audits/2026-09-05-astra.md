# Delta Research audit for GPT-6 Astra

Delta Research's scientific workflow is worth keeping. The highest-value changes are reliable execution and recovery, a test harness that fails when generation fails, fewer conflicting instructions, and cheaper worker models. Use Astra for supervision and GPT-5.6 Sol as the proposed default subagent model, following the user's cost-saving preference. Validate routing with fresh behavioral evaluations.

Audited on September 5, 2026, at commit `bb7f09c381167f4d5885fbd9c634b38cdd76ba5f`. Scope: framework templates, local agent instructions, test runner and representative fixtures, SLURM monitor, installed Codex CLI, and current official OpenAI guidance. Local CLI: `codex-cli 0.150.1`. This was an audit, not a research-loop run. No live Astra comparison, GPU experiment, external publication, or scheduled task was run. Recommendations about model performance remain hypotheses to test.

**Implementation follow-up:** The authorized fixes are now implemented in the working
tree: explicit Astra/high supervision and Sol/medium workers, compact managed
instructions, handoffs and journal confirmations, fresh evaluations that propagate failures, tested logging
and process helpers, scheduler-confirmed completion, and a durable ownership/attempt/
publication journal. Validation passed 192 fixture checks and 33 local behavioral
tests, plus Python compilation and `git diff --check`. Tests cover interrupted state
updates, pending jobs, repeated attempts and failed publication to a temporary local
Git remote. No live model/cluster evaluation or measured cost comparison has run.
The findings and source line references below describe the audited pre-fix revision.
See [testing instructions](../../tests/README.md) and [runtime recovery](../../templates/RUNTIME.md).

**What Astra changes**

Official guidance describes Astra as more sensitive to instructions in skills and agent files, more inclined to clarify consequential ambiguity, sometimes less inclined to delegate, and thorough enough to over-test small changes. It recommends explicit autonomy and completion rules. This makes instruction consistency particularly relevant here. [OpenAI's Astra guidance](https://developers.openai.com/api/docs/guides/latest-model)

The repository launches agent CLIs; it does not implement an OpenAI API client. Consequently, no Responses API rewrite is necessary for this migration. If an API backend is added later, Astra tool calls require Responses, and custom sampling parameters and `none` reasoning need compatibility checks. [OpenAI release notes](https://developers.openai.com/api/docs/changelog#september-2026)

**Verified findings, in implementation order**

| Priority | Finding | Consequence | Recommended change |
|---|---|---|---|
| P1 | Generation and review failures do not fail the harness | A broken or unavailable model can appear to pass | Propagate failure, generate in a fresh directory, validate output provenance |
| P1 | Direct execution and monitoring can misreport success | Failed or over-budget experiments can enter recovery incorrectly | Preserve process exit codes and enforce independent deadlines |
| P1 | Reference logging code is broken | Copying the documented helper can turn successful work into failure | Fix the helper and execute its example in a small test |
| P1 | Resume lacks a durable record of the current phase | Restart can skip an unpublished run or duplicate execution | Persist phase, job IDs, attempt IDs, and publication status |
| P2 | Instruction copies disagree | Unnecessary work, pauses, or inconsistent continuation | Establish one canonical policy and generate concise adapters |
| P2 | Tests reveal expected decisions and mostly check text | Passing scores do not establish research judgment or autonomy | Add fresh, outcome-based, multi-cycle fixtures |
| P2 | Model and effort are implicit; workers can inherit expensive defaults | Results and spending cannot be attributed reliably | Explicitly route workers to Sol; record model, effort, usage, CLI version, and prompt revision |
| P2 | Dense logging conflicts with GPU efficiency guidance | Logging can add synchronization and repeated disk writes | Buffer metrics, flush periodically, preserve final measurements |

P1 means fix before relying on unattended experiments or using the harness to approve migration. P2 means a substantive reliability or optimization improvement.

**1. Make generation and review failures fail the test command**

At [run_tests.py:1597](/Users/jianingqi/Github/delta-research/tests/run_tests.py:1597), nonzero agent exits, missing CLIs, and timeouts are printed without being returned as failures. [Review execution:1694](/Users/jianingqi/Github/delta-research/tests/run_tests.py:1694) has the same behavior. Main then validates existing fixture files and derives its exit status only from those checks at [line 1819](/Users/jianingqi/Github/delta-research/tests/run_tests.py:1819). Review verdicts are printed rather than included in the result.

Reproduction: prepend a temporary fake `codex` executable that exits 42 to PATH, then run the plan fixture. Both generation and review printed the agent failure, reported `21/21 passed`, and exited **0**. No model was invoked and no fixture was changed.

Fix: return structured execution results; fail on nonzero exit, timeout, unavailable CLI, missing output, or invalid review result. Write generated artifacts into a unique evaluation directory, separate from checked-in examples. Record the invocation ID and validate only artifacts created by that invocation. Set an explicit working directory. Preserve stdout/stderr and termination reason; terminate child process groups on timeout. A review should return a machine-readable verdict whose failure affects the command's exit status.

**2. Preserve execution failure and make timeouts independent of output**

The direct-mode command at [OBSERVABILITY.md:400](/Users/jianingqi/Github/delta-research/templates/OBSERVABILITY.md:400) pipes Python into `tee` without establishing `pipefail`, but line 403 claims it returns Python's status. In a clean Bash shell, a Python exception followed by successful `tee` returned **0**. Use a launcher with explicit pipeline failure handling and capture the experiment's exit status. Apply the same correction to the smoke command at line 368. The background `tail -f | grep` example at line 411 also has no terminal exit mechanism.

The monitor checks elapsed time only when a read has received no line for 30 seconds at [wait_for_job.sh:90](/Users/jianingqi/Github/delta-research/scripts/wait_for_job.sh:90). A producer writing every 0.1 seconds exceeded a requested one-second timeout, finished after **3.12 seconds**, and returned **0**. Check a deadline independently of incoming lines and bound each wait by the remaining time.

The monitor also accepts the first success marker at [line 98](/Users/jianingqi/Github/delta-research/scripts/wait_for_job.sh:98). A synthetic log containing DONE followed by BLOCKER returned success. This is a robustness test, not evidence that current experiments emit those markers in that order. Make job success depend on the launcher finishing successfully across all ranks; use markers as progress evidence. For SLURM, reconcile scheduler completion/exit status where available, and distinguish scheduler-query errors from a vanished job.

Finally, a monitor timeout does not cancel a SLURM job, yet [recovery:524](/Users/jianingqi/Github/delta-research/templates/OBSERVABILITY.md:524) groups timeout with failures that may be resubmitted. Check the existing job before resubmission. Continue monitoring it or stop it under the recorded job-control policy; do not accidentally run two copies.

The helper creates `self.log_file` but closes `self.train_log` at [OBSERVABILITY.md:149](/Users/jianingqi/Github/delta-research/templates/OBSERVABILITY.md:149). Correct the method names, make cleanup safe on repeated calls, and ensure cleanup failure cannot hide the original experiment error. Consider moving this small reusable helper into tested Python source and referencing it from the markdown. That reduces repeated model-generated infrastructure without moving scientific decisions out of the templates.

**4. Make resumption explicit before adding more scheduling**

[Phase 1:92](/Users/jianingqi/Github/delta-research/templates/SUPERVISOR.md:92) resumes only the next ledger ID when PLAN and BLOCKER exist without a ledger row. It does not specify recovery after a job was submitted but the session ended, after a report was written without compression, or after compression succeeded but push failed. [Phase 6b:269](/Users/jianingqi/Github/delta-research/templates/SUPERVISOR.md:269) happens after the ledger update. The [BLOCKER table:673](/Users/jianingqi/Github/delta-research/templates/SUPERVISOR.md:673) includes publication failures but says not to create a report or ledger row, although both already exist at that point.

Add a small durable execution record: run ID, current phase, attempt IDs, active jobs/processes, completed conditions, deadline, pre-run commit, and pending publication commit. On every entry, reconcile this record with artifacts and job state before allocating work. A failed push should retry publication of the same completed experiment without changing its scientific result or incrementing the run count again. Use atomic writes and one supervisor lock so two wakeups cannot both submit the next run. Keep scientific beliefs in STATE.md; the execution record tracks operations only. Do not repurpose or edit generated `.delta-loop/LOOP.md` or `.delta-loop/POLICY.md`.

Evaluate budget and stop requests before launch as well as after a cycle. Persist cumulative usage and deadlines across sessions. The current [budget boundary:670](/Users/jianingqi/Github/delta-research/templates/SUPERVISOR.md:670) is a prose rule, with no required persistent usage counter in the state template.

The [Codex scheduling instructions:326](/Users/jianingqi/Github/delta-research/templates/SUPERVISOR.md:326) prescribe `at` and a fresh CLI session. Make this host-specific: continue in the active session when possible; use the available native same-task scheduling facility in the desktop app for deferred continuation; reserve an explicitly configured external scheduler for CLI hosts. Scheduled local work requires the host and app to remain available. [Official scheduled-task documentation](https://learn.chatgpt.com/docs/automations?surface=app)

Recommended behavioral fixtures:

| Scenario | Required outcome |
|---|---|
| Runnable plan with adequate user authorization | Starts measurement without another permission question |
| Smoke succeeds; baseline/treatment still pending | Continues same run until the required comparison is complete |
| Scientific evidence remains inconclusive | Reports uncertainty without inventing a successful result |

**7. Use cheaper workers and measure total cost per valid experiment**

Both Codex invocations omit model, effort, explicit cwd, and structured event output at [run_tests.py:1590](/Users/jianingqi/Github/delta-research/tests/run_tests.py:1590) and line 1688. They therefore inherit settings that may vary between machines or sessions. Add model/effort options and record the effective configuration and framework revision. Local CLI help confirms `--model`, `--cd`, and `--json`; `--approve-for-me` is supported and does not need replacing. The official configuration reference documents `model_reasoning_effort`. [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)

The user explicitly wants lower-cost subagents. Proposed initial routing:

| Responsibility | Proposed model | Starting effort | Ownership |
|---|---|---|---|
| Scientific question selection, experiment design, evidence interpretation, difficult escalation | `gpt-6-astra` | Preserve the supervisor's effective setting initially | Supervisor owns beliefs and accepts the scientific conclusion |
| Experiment implementation, execution, bounded debugging, report draft | `gpt-5.6-sol` | Medium; evaluate high for difficult code | Default subagent owns the complete assigned experiment |
| Narrow extraction or formatting with mechanically checkable output | `gpt-5.6-terra` | Low or medium, after task-specific validation | Optional cheaper helper; cannot decide scientific validity |
| Job waiting, metric aggregation, file validation, routine bookkeeping | Deterministic scripts | N/A | No model call when code already performs the operation |

Keep the initial rollout simple: Astra supervisor plus Sol workers. Terra is a subsequent candidate for narrow tasks, not a required extra agent in every cycle. Lower-price workers should be explicit in the spawning/configuration path, including nested helpers; do not rely on inheriting the supervisor's model. Do not silently substitute Astra when a configured cheaper model is unavailable.

At current Standard API short-context rates per million tokens, Astra is $10 input / $50 output and Sol is $4 / $20. Sol therefore costs 60% less for equal token counts and billing categories; Terra is $2 / $12. Sol pricing is promotional at least through November 21, 2026. These are API prices, not measured savings in this repository. [Official API pricing](https://developers.openai.com/api/docs/pricing)

Codex subscription allowance consumption also depends on model, context, reasoning, tools, and caching. Do not convert API dollar ratios directly into subscription quota savings. [Codex usage guidance](https://learn.chatgpt.com/docs/pricing#what-are-the-usage-limits-for-my-plan)

Cheaper tokens and fewer tokens are separate improvements. To reduce token volume, give a worker a fresh, bounded handoff containing the question, plan path, relevant resource paths, constraints, and expected outputs. Avoid copying the entire supervisor conversation. Reuse that worker for the same run while its context remains relevant. Return a short completion message with decisive metrics, artifact paths, and unresolved issues; keep the full report in its file. Let the supervisor inspect decisive evidence without replaying every log or implementation step. Compact away irrelevant context rather than restarting and rediscovering the same work.

Escalate a precise unresolved issue to the existing Astra supervisor after bounded unsuccessful diagnosis, or immediately when scientific interpretation needs a decision. Include the error, attempted fixes, and exact code/metric paths. The supervisor can resolve the hard point and send a focused continuation to Sol. Avoid automatic Astra reviewer subagents and unbounded chains of helpers. More parallel agents can increase total tokens even when they shorten elapsed time.

Evaluate model-only changes first with fixed prompts and effective effort, then test routing, shorter handoffs, and worker effort separately. Record input, cached input, output/reasoning usage where exposed, model, effort, retries, supervisor review overhead, and estimated API cost when applicable. Count reasoning within output billing rather than charging it twice. Measure total model cost per scientifically valid completed experiment, including failed attempts and escalations; also track wall-clock time and wasted compute. Keep scientific adequacy and the approved time/compute bounds as requirements. No live comparison has established the optimal routing or effort yet.

Keep one owner for the complete experiment. Specify that independent implementation or analysis tasks may be delegated only when they save time, have disjoint writes, and return bounded results. The owner reconciles all required conditions into one report. Avoid automatic extra reviewer agents for every successful command. Preserve an inline fallback on hosts without subagents; it currently conflicts with the supervisor's unconditional prohibition on direct execution.

**8. Make telemetry support the wall-clock objective**

[INFRA:126](/Users/jianingqi/Github/delta-research/templates/INFRA.template.md:126) discourages scalar extraction on every GPU step, while [OBSERVABILITY:271](/Users/jianingqi/Github/delta-research/templates/OBSERVABILITY.md:271) formats loss into a string every step and immediately flushes the text log. The helper keeps every history item in memory and rewrites the full history every 1,000 entries; saving does not clear memory despite its comment.

Use a configurable logging interval, buffered append-only records, and a small final results file. Preserve the measurements needed for the hypothesis and per-rank useful-work counts. Keep accurate sample-weighted aggregation and unchanged batch/seed semantics across comparisons. Retain the existing all-confirmed-GPU policy, DDP training default when a replica fits, example-sharded inference, and concurrent independent conditions where scientifically valid. The current supervisor already distinguishes these layouts; tuning should preserve that distinction.

**What to retain**

The one-run/one-answer rule, direct evidence requirement, bounded repair, editable short plan, complete baseline/treatment package, honest inconclusive results, supervisor ownership of beliefs, and explicit scientific finish condition are good foundations. The 80-word answer-first report opening and optional plots already address verbose reporting. Preserve recorded GPU and publication authorization so subsequent cycles do not ask again. For scoped API, dataset, or methodological uncertainties, keep source lookups bounded inside the experiment; any broader relaxation of literature recovery should be an evaluated policy change.

**Suggested rollout**

1. Fix test failure propagation, logging helper, pipeline exits, and monitor deadlines. Add local tests that reproduce the failures above.
2. Add durable resume/publication state and a single-owner lock. Test interruptions at each phase and live-job reconciliation.
3. Consolidate policy copies and refresh generated instructions. Make scheduling host-specific and shared-file ownership explicit.
4. Run an isolated model-only Astra comparison, then evaluate an Astra supervisor with Sol workers, shorter handoffs, and worker effort. Adopt lower-cost routing when it preserves completion/recovery correctness and meets the approved time-to-answer bounds. Consider Terra only for narrow tasks that pass those evaluations.
